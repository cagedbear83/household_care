# Household Care

Full requirements live in [IP-App-Specification.md](IP-App-Specification.md). This repo implements:

- **`backend/`** — Node.js/TypeScript + Express + PostgreSQL (Prisma). Owns every rule the spec requires to be enforced server-side: the append-only, hash-chained audit log, the 36-hour weekly authorization engine, geofence verification, and role/household scoping.
- **`mobile/`** — Expo (React Native) app for the Individual Provider: check-in/out, the every-visit task checklist, and periodic location pings while a shift is active.

The same Expo app also runs in a browser (`npx expo start --web`) and serves the client, administrator and family screens.

**Branches:** `development` (local building), `staging` (pre-production checks), `main` (production). See [BRANCHING.md](BRANCHING.md) for how work moves between them.

## Why this split

The spec is explicit that a browser alone cannot promise reliable background location collection on Android, and that GPS only indicates the phone's reported position, never identity or honesty. The IP's check-in/out and in-shift task flow therefore needs a real mobile app with native location permissions and lifecycle handling; the authorization, audit, and hour-cap rules all live on the server so no client (mobile or otherwise) can be trusted to enforce them itself.

## Backend

```bash
cd backend
npm install
npm run dev:db       # starts a local Postgres 18 (no admin rights / Windows service needed — see below)
npm run prisma:migrate
npm run seed          # creates a household, admin/client/ip users, task templates, and a shift starting now
npm run dev
```

This environment had no Docker and no admin rights to install PostgreSQL as a Windows service, so `npm run dev:db` runs a real Postgres 18 binary (via the `embedded-postgres` package) as a plain user process on port 55432, with its data under `backend/.pgdata/` (gitignored). `backend/.env` already points at it. Leave `dev:db` running in a terminal while you work; `Ctrl+C` stops it cleanly. For a real deployment, point `DATABASE_URL` at a proper managed Postgres instead (Neon, Supabase, RDS, a Docker container, etc.) — nothing about the schema or migrations is specific to the embedded binary.

Verified end-to-end against this local database: login → fetch today's shift → check-in (geofence + schedule + weekly-cap checks, task instances auto-created) → complete a task → a photo-required task correctly rejected without evidence → checkout → event hash chain integrity (`npm run verify:chain`) confirmed unbroken.

### What's implemented

- Append-only, hash-chained `Event` log (`src/services/event.service.ts`) — every domain write goes through `appendEvent`; nothing updates or deletes a row.
- 36-hour weekly cap + scheduled-end authorization engine (`src/services/authorization.service.ts`), enforced atomically via row locks so concurrent devices/check-ins can't double-spend the weekly allowance, plus a per-minute cron sweep (`src/index.ts`) that closes an authorized window server-side even if the IP's phone is offline.
- Geofence verification (haversine distance + accuracy-aware VERIFIED/UNVERIFIED/FAILED classification) on check-in, checkout, and periodic pings.
- Check-in/out/location-ping/task routes, scoped to the authenticated IP's own household and shift.
- Task lifecycle: visit-frequency `TaskTemplate` rows are snapshotted into `TaskInstance`s at check-in; complete / not-needed / unable-to-complete / client-decline-reported transitions, each as its own event.
- Auth: bcrypt + JWT, with every request re-checking the user's `active`/`accessRevokedAt` status (so a revoked family account loses access immediately, not just at token expiry).

- Admin/client scheduling API (`/admin/*`, ADMIN and CLIENT roles only): create a day's shift (rejects same-day duplicates, overlaps, and anything that would push the IP past 36 scheduled hours in the workweek — serialized under a row lock so concurrent requests can't slip past the cap), mark vacation/sick/unavailable days, create recurring weekly rules and expand them into shifts for a date range, and create/edit task templates (before/after recorded in the audit log; past task snapshots are never rewritten). Wall-clock times that don't exist on a daylight-saving gap are rejected.
- Audit log hardening: a per-household lock plus link-based chain walking, so concurrent writes can't fork the chain and verification reports forks/orphans.
- Integration tests (`npm test`, runs against the local dev DB in an isolated throwaway household): cap boundary at exactly 36h, concurrent-request race, DST gap/elapsed-time, cross-household isolation, recurring expansion, template audit, chain integrity.

- Schedule screen in the mobile/web app (`mobile/src/app/schedule.tsx`): after signing in, the client and administrators land here and IPs land on Today. Shows a Monday–Sunday week with prev/next navigation, an hours-vs-36 bar, each day's shift or time off, an inline form to add a shift/vacation/sick/unavailable day, and a weekly-pattern card that saves a pattern and fills the next four weeks (reporting which days were skipped and why). Server rejections are shown as written.

- Changing and cancelling shifts: a change replaces a not-yet-started shift with a new version (the old row is kept, linked, and marked superseded) and requires a reason that goes to the audit log; cancelling works the same with no successor. Shifts that have been checked in, or have already ended, cannot be changed (that would erase missed work). Replacements go through the same cap/overlap/duplicate rules, and a changed or cancelled shift can no longer be checked into.
- Task template screen (`mobile/src/app/templates.tsx`): list by area, add, edit, deactivate/reactivate. Changes apply to future shifts only; past tasks keep their snapshot.
- Photo evidence for photo-required tasks (the clean-sink check): the in-app camera (`mobile/src/app/capture.tsx`, no gallery or file picker) first asks the server for a one-use, 10-minute capture challenge bound to the user, shift and task. The upload is accepted only against an unused challenge while the shift is checked in and inside its authorized window. The server checks it is a real JPEG/PNG, hashes the original (SHA-256), stores it write-once, makes a re-encoded copy with embedded metadata (GPS, device) stripped for viewers, records a fresh location reading tagged `PHOTO_CAPTURE` (a wrong or unverifiable location is accepted but recorded as failed/unverified and raises an alert), and writes an `evidence_accepted` audit event. The task cannot be completed until a photo is accepted. Admins/client (and family with approved access) read the stripped copy via `/evidence/:id/image`; IPs only see a "photo accepted" flag. Device-claimed capture time is stored as a claim, never as proof. The hash protects integrity, not truth.
- IP responses are built from an explicit allow-list (`backend/src/services/ip-dto.ts`), so IPs no longer receive audit timestamps or internal ids.
- The app signs out automatically if the server rejects a saved login.

- Review screen (`mobile/src/app/review.tsx`, the client's landing page; administrators get the same screen read-only): everything waiting on a decision across all days, plus a day browser showing each shift, its check-in/out and every task by area with its state, photos and full history. Photos are the metadata-stripped viewer copy with upload time, location result and a short SHA-256 fingerprint.
- Client decisions (CLIENT role only; the server refuses administrators and IPs): **Approve**, **Dispute** (a reason is required and is shown to the IP; admins get an alert), **Review later** (local to the screen), and for a decline the IP reported on the client's behalf, **Yes, I declined** or **No, I want this done**. Each is an atomic state change plus its own audit event. After a dispute the IP submits **corrected work** only while their shift is open, and for photo tasks only with a photo taken after the dispute; the client can then approve or dispute again. The original completion, each dispute, each corrective submission and the final approval stay as separate events. Task endpoints now only accept a transition from the states it is meant for, so an IP can no longer re-complete a task the client already approved. The IP's Today screen refreshes every 20 seconds while a shift is open (no push notifications yet).

- Family viewer and invitations: the client (or an administrator, to help with setup) adds a family member by **email address or phone number**. The invitation goes to that one contact as a one-use link (7 days; only a hash of the token is stored). Opening it, the person (1) confirms their **first and last name**, confirms that the email/phone the invitation reached is theirs, and chooses a password; (2) **adds the other contact** (a phone if invited by email, an email if invited by text); (3) enters a **6-digit code** sent to it (10 minutes, 5 tries, 30 seconds between sends). Only then is the account activated and signed in, so each family member gets their own login, usable with either contact. Resending replaces the old link. The client can approve or withdraw photo-and-time access per person and can turn access off, which takes effect on the very next request. An administrator can invite and resend but cannot grant photo/time access or revoke. Full audit events for every step (contacts are masked in the log).
- What family can see: the Review screen read-only. Without the client's approval they get task status and history **without times or photos** (the server omits them; it is not just hidden). With approval they also see photos, check-in/out times and timestamps. They cannot approve, dispute, schedule, or reach IP or admin endpoints.
- Comments: the client, administrators and family can comment on **any task, complete or not, and on individual photos** (a family member needs photo approval to comment on a photo). Comments are append-only (never edited or deleted), recorded as audit events, and not shown to IPs.
- Chat: one **household group chat** plus **private direct messages** between any two people (client, administrator/case manager, family, IPs). Direct messages are visible only to the two people (not even administrators); in the group, a person sees messages from when they joined. A floating **Messages** button on every main screen shows the unread count; the list and open conversations refresh every few seconds (polling, not live push). The administrator account is labeled "Administrator (Case Manager)". Messages are 1-2000 characters and are not edited or deleted.
- Sign-in accepts an **email address or a phone number**. Sign-in and the public invitation endpoints are rate limited per IP (in memory, one server process).

**Delivery of invitations and codes.** Real delivery is configured in `backend/.env` (see `.env.example`): `SMTP_URL`/`EMAIL_FROM` for email and `TWILIO_*` for text messages. With none configured (development), nothing is sent: messages are printed in the backend console and stored in an outbox table, and the invite screen shows the link (and the 6-digit code) so you can walk through signup yourself. The SMTP and Twilio code paths have **not** been run against live services; try them with real credentials before relying on them. Invitation links point at `APP_BASE_URL` (default `http://localhost:8081`), so set it to a real web address, or your computer's LAN address, for a link to open on someone else's phone.

- Password reset: "Forgot your password?" on the sign-in screen. Enter the email address or phone number on the account and a 6-digit code is sent there (15 minutes, 5 tries, 60 seconds between requests, 5 an hour). The request always answers the same way, so it cannot be used to find out who has an account. Changing the password **ends every existing session** on the account (the auth check rejects anything issued before the reset), spends all open codes, and sends a "was this you?" notice. New passwords must be at least 10 characters. Sign-in and reset endpoints are rate limited.
- Food disposal (`mobile/src/app/supplies.tsx` for the IP, `food.tsx` for the client and administrators): during a checked-in shift the IP asks to throw something away with the **item, its exact location, a reason, any date on the label, a replacement to buy, and an in-app photo** (the same one-use ticket, hashing, write-once storage, metadata-stripped viewer copy and location check as task photos). It goes to the client (texted or emailed, and visible to administrators). **Nothing is thrown away until the client approves**; only then can the IP record the actual disposal. A declined request stays in place and shows the client's message to the IP. If nobody answers in 30 minutes (`FOOD_RESPONSE_MINUTES`) the item stays in place and the administrator is alerted once with the item and location (the photo is on the request); a late answer still counts. An **immediate hazard** is its own explicit report (reason and what was done are required, photo optional): it is recorded as an exception, the client and administrators are told right away, and the client acknowledges it. It is never treated as an approval. The client and administrators see a full history (who asked, who decided, who threw it away, and when); the IP sees only status and the client's answer, with no audit timestamps.
- Shopping list (`mobile/src/app/shopping.tsx`): item, quantity if known, where it is kept, needed/low/out, and a "bought / restocked" acknowledgment (kept as history for 30 days, as is "removed"). The same item typed differently ("Eggs", " eggs! ") **merges** into one row (the worse status wins, blanks are filled, a counter shows how often it was mentioned), even when several people add it at once. Items arrive three ways: added by the client or administrator, **automatically after an approved item is actually thrown away** (the replacement, with where it was kept), and from an **IP's low-supply report** ("a little left" / "none left"; the client and administrator are told when it is new or gets worse). There is no shopping duty for the IP and the IP cannot edit the list. Nothing is guessed from meals: the IP is asked whether there is any left.
- Check-in fix: a forgotten checkout from an earlier day no longer blocks the next check-in (it stays on record as missing a checkout, never filled in); only a shift whose authorized window is still open blocks another.
- Notifications for these (new food request, hazard, no answer, low supply) are texted or emailed to the client and administrators through the same delivery as invitations (see below); in development they print in the backend console and are stored in the outbox table. Push notifications are not built.

- Alerts screen (`mobile/src/app/alerts.tsx`, client and administrators; administrators now land here after signing in). Alerts are their own records (`Alert`, still tied to the permanent `alert_raised` audit event) with **read state per person**, so one administrator reading an alert does not clear it for another. A badge shows on the Alerts tab and on a floating **Alerts** button next to Messages; when anything is urgent the button says **"Urgent alerts"** (urgent is always a word and a red frame, never color alone). Urgent items that nobody has dealt with are listed first and labeled **URGENT**, new ones **NEW**, finished ones **HANDLED**. **Open** takes you to the screen where you can act (food, review, schedule, shopping) and marks the alert read; **Mark as read**, **Mark all as read** and **Read aloud** are there too. Action-required alerts clear themselves as **handled** when the matter is dealt with (a food request is answered, a hazard acknowledged, an item bought, a reported decline confirmed or denied). The same matter never alerts twice (a dedupe key per matter), and an alert is only visible to the roles it is for (the check-in alert, for example, is administrator-only). The screen refreshes every 15 seconds (polling; no push).
  - What raises an alert: location that could not be verified, time past the authorized window, a hazard, a food request nobody answered, an item running low or gone, a disputed task, a decline the IP reported on the client's behalf, an IP checking in or out **early**, an IP leaving with **tasks not done**, and an unusually fast run of completions (default 15 or more within a minute, `COMPLETION_BURST_THRESHOLD`), worded **"may need a look"** and never as proof of anything.
  - Text/email delivery comes from a queue (`deliverPendingAlerts`, run every minute): each alert is sent once to the people it is for, a failed send is retried up to 3 times, and the result is in the outbox table. Alert types that already notify people when they happen (food requests, hazards, low supplies) are not sent twice.
- Spoken summaries and the **Hear** screen (`mobile/src/app/hear.tsx`; client, administrators and family; not the IP). The server writes the exact sentences (`backend/src/services/summary.service.ts`, `GET /summaries`) so every device says the same thing and the wording is tested; the app only reads the text aloud and shows it in writing too. Available: **full update**, **new alerts**, **what needs a decision**, **what is left today**, **what was done today**, **when the IP checked in**, **hours this week against the 36-hour limit** (counting a visit in progress), **shopping list**, and **unread messages**. "Done today" **asks first** ("2 tasks were completed today. Would you like me to read them out loud?") with visible **Yes**/**No** buttons, and the list is only read after a yes. Long lists are trimmed ("…and 22 more"). Quiet things say so plainly ("Nothing is waiting for a decision."). Family members get only what they are meant to hear: no alerts, decisions, shopping, and **no times, hours or photo counts unless the client approved that for them**. A large **Stop** button is always visible, reading speed is **Slow / Normal / Fast** (remembered on the device), and a setting **"Read new urgent alerts aloud"** (off by default, remembered per person) reads a new urgent alert as soon as the open app sees it; urgent ones already waiting when you sign in are not read automatically.
  - Voice commands: on the web version, a **Speak a command** button uses the browser's speech recognition ("full update", "what is left", "what needs my decision", "stop", "yes", "no", "slower", "repeat"…). The microphone is only on after you tap and stops by itself. The phrase parser (`mobile/src/lib/voice-commands.ts`, checked by `npm run check:voice`) returns nothing rather than guessing. Every command is also a button. **Not built:** voice input on the phone apps (it needs a native speech-recognition module and a development build), voice approvals (approving or disputing by voice), and hands-free listening in the background.

- **Home** (`mobile/src/app/home.tsx`): everyone lands here after signing in, and every other screen has a **Home** button at the top. It is one big button for each place the person can go, in this order: Alerts (with the unread count, and "Urgent alerts" in a filled box when anything urgent is waiting), Review, Food, Shopping, Schedule, Tasks, Family, Hear, Reports, Messages (unread count) and Settings. The client and administrators get all of them; a family member gets Review, Hear, Reports, Messages and Settings; the IP gets Today (the shift screen, now `today.tsx`), Food and supplies, Messages and Settings. The old tab strip was replaced by the Home button, and the floating Alerts/Messages buttons are hidden on Home since it has them already.
- **Settings** (`mobile/src/app/settings.tsx`, any role): change your name; change or add the **email address or phone number** you sign in with (a 6-digit code goes to the NEW one and nothing changes until it is entered: 15 minutes, 5 tries, one a minute, 5 an hour; the old contact is told it changed); change your **password** (needs the current one, at least 10 characters; other devices are signed out and this one gets a fresh session). Everything is recorded in the audit log with contacts masked and passwords never stored there. A family member also sees whether the client approved photos and times for them. Role, household and approvals are shown but only the client controls those.
- **Reports** (`mobile/src/app/reports.tsx`, `backend/src/services/report.service.ts`; client, administrators and family; not the IP): a **day, week (the household's workweek), month or custom** range (up to 366 days) with Previous/Next and a date box to jump to any date. Each report states the dates, timezone, when it was made and by whom. **Task results** count each outcome separately (submitted, approved, waiting for review, disputed, declined and confirmed, not needed, unable, not done at the end of the visit, still open) with four percentages whose formulas are printed beside them: completion (submitted divided by all assigned, disputed ones included and shown separately), approved completion, coverage and resolution. Declines, not-needed and unable are never counted as work done. Counts come from the task list snapshotted at check-in, so editing a template later never changes an old report. **Attendance and exceptions** shows scheduled, authorized (the minutes counted toward the 36-hour limit, which stop at the authorized end) and observed (check-in to checkout) time **separately**, weekly totals against the limit, each visit, days off, and a list of exceptions: early or late check-in, early checkout, time past the window, no checkout recorded, a visit with no check-in, tasks not done when the visit ended, location that could not be verified, disputes (with the client's reason), declines the IP reported, corrective work, activity that may need a look, and automatic authorization closures. Flags are prompts to look, never findings. A family member without the client's approval for times gets the task counts only (the server leaves attendance and exceptions out). **Print or save as PDF** opens the system print window (the page is built on the device, so the server stores nothing). Reports are made on request, sent with no-store headers, and not saved; the only record kept is an audit event saying who made one for which dates.

- **Corrections** (`backend/src/services/correction.service.ts`, `mobile/src/app/corrections.tsx`). The IP can only **report** a mistake ("Report completion error" on any task that has something recorded, or on their check-in or checkout), with a reason; this is an append-only request that changes nothing, raises an alert for the client and administrators (the text message names the task but not the IP's words), and stays visible to the IP with the answer. The client or an administrator then **appends a correction** with a reason, linked to the original recorded event: *completion recorded in error*, a *note about check-in or checkout*, or an *other note*. The original event is never changed or removed; the correction is its own permanent record with who made it, their role and why, plus its own audit event. A completion error moves the task to a separate state (`COMPLETION_ERROR_CORRECTED`): it stops counting as done, the client can no longer approve it, and the IP can do it again while the visit is open (a photo task needs a new photo). Attendance corrections are notes beside the recorded times; **observed check-in and checkout times are never changed or filled in**. A report can also be answered **without a correction** (the reason is kept and shown to the IP). The IP is texted or emailed that their report was answered, with no details. Everything shows in a task's history, in Reports (corrections as exceptions, notes under the visit, and corrected tasks counted separately and never as done), and the client and administrators cannot correct anything in another household.
- **Retention** (`backend/src/services/retention.ts`) is a **fixed rule, not a setting**: every record is kept at least **ten years** from when it was recorded, and nothing (no role, no screen, no environment variable) can change that. Ten years covers the longest period found for this kind of employment (the Illinois wage-claim window is ten years; federal and Illinois payroll, pay-stub and leave records are three years; federal employment-tax records are about four to five), but it is a product decision, not legal advice. Records tied to a dispute that is not resolved are kept regardless of age. The module only answers "until when" and "what could be archived"; **the app never deletes anything**. After ten years records are meant to be archived and compressed to cheaper storage, which is a separate job still to be built. Evidence photos are meant to follow a shorter schedule (to be defined), with their hashes and audit events kept for the full period. A test fails if anyone adds a way to change the period.

- **Program rules (from the Home Services Program forms and the SEIU agreement).** **Workweek** is Sunday to Saturday (the agreement's overtime week); the **weekly limit** is the Service Plan hours (36 here). **No more than 8 scheduled hours in a day**, for everyone; a warning is raised at checkout when more than 14 hours were recorded in a rolling 24 (the program needs the counselor's approval beyond 16). The **primary family member** (the first family member to finish signing up) has the client's access and the client's notifications everywhere (the server treats them as the client, and the audit log still shows who acted); the client cannot remove them, only an administrator can reassign or remove with a reason. **Away mode** (hospital, vacation, other; set on Home by the client, an administrator or the primary family member) stops the IP checking in or completing tasks and taking task photos, never checkout; the IP is told work is paused, never why. **Photos are removed one year** after they were accepted (fixed, a daily job; an approval never removes one; photos tied to a dispute, corrective work or a reported mistake, or from dates covered by a **preservation** ("keep everything for certain dates", on Reports, for the client's side), are kept; the hash and audit event always stay). The review question under a photo is "Did the IP complete this task properly?" (Yes, or No, do it again, which is the existing dispute). On **Sunday morning** the IP is emailed their own hours for the week just ended (totals only, not the official time sheet or EVV); on the **15th and the last day of the month** the client and primary family member are reminded to review hours before signing the time sheet.

- **Wellbeing check-ins (PHQ-2 and GAD-2).** An administrator, once the client has agreed (recorded), starts a PHQ-2 (mood) and/or GAD-2 (anxiety) check-in every 1, 2 or 3 days. The client (and the primary family member) sees a "check-in is waiting" card on Home and a Check-in screen with large answer buttons and "Read it to me"; "Not today" skips that turn and the client side can pause or resume a check-in. The standard published questions and scoring are used, unchanged; a total of 3 or more is flagged. **Only administrators can read answers and scores** (Wellbeing screen). A flag alerts administrators and texts the primary family member a message with no score and no topic in it; the client gets a kind message with 988 and 911 and is never alerted about themselves. The IP sees nothing about it, and the audit log records only that a check-in happened and whether it was flagged, never the answers or score. It is a screening aid, not a diagnosis or an emergency service.

### Not built yet (next steps, roughly in priority order)

Production evidence storage with enforced retention (the dev store in `evidence-store.ts` is local disk and is the only file to swap for S3 Object Lock or similar); weekly/monthly task distribution across visits; step-up (PIN/biometric) re-authentication for sensitive admin actions; marking unresolved tasks as missed when a shift ends, and carrying them to an admin-approved later shift.
2. Photo evidence has not been exercised on a real camera yet: the server flow is covered by tests and a live HTTP run with a 2 MB photo, and the app compiles and bundles, but the capture screen still needs a hands-on run on the emulator/phone.
3. Requesting a task, push notifications for disputes, comments, chat and food requests (today the screens poll and urgent items are texted or emailed), voice input and voice approvals on the phone apps, and a way for a family member to see the shopping list.
4. Reports still to do: a report of an IP's own hours for the IP, and a spreadsheet (CSV) export. Retention still to do: the archive-and-compress job for records past ten years, and a shorter life for evidence photos (the app deletes nothing except photos after their year). Also a dashboard for administrators and flagging an earlier shift with a missing checkout on the administrator's screens. Alerts raised before the alerts screen existed are only in the audit log (a development database will show none until new ones arrive).
5. Real SMS/email delivery has code but is untested against live providers (see below). Reading aloud uses the device's own voice (the browser's on the web); it has been checked in a browser, not yet by ear on a phone or with a screen reader.
6. True background location collection (the mobile app currently pings only while open in the foreground — see the comment in `mobile/src/lib/location.ts`); this needs a native dev build with `expo-task-manager` and an Android foreground service, validated on a real device.
7. Reports (daily/weekly/monthly/custom, Attendance & Exceptions, PDF export) and retention/archival.
8. Accessibility pass on real devices with TalkBack/VoiceOver (the mobile screens have accessibility labels/roles but haven't been screen-reader-tested).

## Mobile (IP app)

```bash
cd mobile
cp .env.example .env   # set EXPO_PUBLIC_API_URL to reach your backend
npm install
npx expo start
```

Scan the QR code with Expo Go, or run `npm run android` / `npm run ios` for a simulator/emulator. Uses Expo Router (routes in `mobile/src/app/`) per `mobile/AGENTS.md`.

Type-checks and lints clean (`npx tsc --noEmit`, `npx expo lint`), and `npx expo export -p android` bundles successfully. The backend has been smoke-tested directly via its HTTP API end-to-end (see above), but the mobile app itself has **not** yet been run on a physical device, simulator, or emulator — that's the next thing to do.
